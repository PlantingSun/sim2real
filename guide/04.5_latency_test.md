# Step 4.5：Orin 延时与频率分层测试

本节只测量频率，不修改模型、XML 或控制参数。三项测试按顺序进行。

## 1. 纯 policy

不初始化 DDS，只测量观测构造、PyTorch 推理和动作转换：

```bash
python scripts/policy/benchmark_policy_latency.py \
  --policy go2w --threads 1 --warmup 50 --iterations 500 \
  --log logs/policy/go2w_latency.csv
```

输出 mean/P50/P95/P99/max 和平均 Hz。`50 Hz` 的单帧预算是 20 ms；重点看 P99 和
超时次数，不只看平均值。

## 2. MuJoCo pipeline + policy

```bash
python scripts/simulation/test_mujoco_pipeline.py --auto-start --frames 500
```

程序每 50 个 policy 周期打印一次实际仿真 policy Hz，用于区分 MuJoCo 同步循环带来的
影响。

## 3. 实机 LowCmd + policy（只打印 action）

机器人必须吊起并由人工保护。该模式仍发送固定初始站姿和 500 Hz LowCmd，但 policy
生成的 `MotorCommand` 不会发送：

```bash
python scripts/real/test_policy_real.py --control fixed \
  --vx 0 --vy 0 --vyaw 0 --print-only \
  --log logs/real/policy_print_only.csv
```

按原流程操作 `1`、吊起、`2`。日志中的 `loop_dt_ms`、`inference_ms` 和时间戳用于比较
实机线程负载；退出时仍会进入紧急阻尼。

## 判定

- 纯 policy 已低于 50 Hz：优先处理 PyTorch/CPU 线程和模型格式（再比较 ONNX）。
- 纯 policy 正常、MuJoCo 变慢：检查仿真同步和 OpenMP 竞争。
- 前两项正常、实机 print-only 变慢：检查 DDS 500 Hz 发布线程、CPU 调度和网口配置。
- 三项频率都正常但实机动作异常：再检查状态/动作映射、单位、模式释放和控制权冲突。

## CPU 分核实验

先查看 Orin 可用 CPU：

```bash
nproc
lscpu -e
taskset -pc $$
nproc --all
```

`lscpu -e` 显示硬件 CPU；`taskset -pc $$` 显示当前 shell 实际允许使用的 CPU。
只有后者列出的 CPU 才能用于分核。如果只允许 CPU 0，就暂时不能做分核实验，需要先
检查系统的 cpuset/cgroup 限制。

例如在确认 CPU 1、2、3 都允许使用后，将 policy 放在 CPU 2、3，将 500 Hz LowCmd
线程放在 CPU 1：

```bash
python scripts/real/test_policy_real.py --control fixed \
  --vx 0 --vy 0 --vyaw 0 \
  --policy-cpus 2,3 --lowcmd-cpu 1 --torch-threads 2 \
  --log logs/real/policy_affinity.csv
```

终端应出现 `policy 进程绑定 CPU` 和 `LowCmd 线程绑定 CPU`。先只比较 `--torch-threads
1` 与 `2`，不要一开始使用全部核心；每次实验只改变一个参数，并记录 CSV 中的实际
policy Hz。若 CPU 编号不存在，脚本会报告绑定失败并继续使用系统默认调度。
