# 22.5：Go2WWMP 自动日志格式与使用

本文定义正式入口 `scripts/real/run_go2wwmp_unitree.py` 自动生成的两类实验文件，供实验复盘、
数据分析和后续程序对接使用：主 JSONL 记录控制诊断，旁边的 `_obs/` 目录记录 timestamp、
策略观测和深度。它们适合回答“策略收到了什么、算出了什么、当时数据有多新”，但不能单独
证明电机实际执行了目标。

`scripts/real/test_policy_go2wwmp_real.py` 的验收日志复用大部分字段，但它只在显式传入
`--log` 时生成，并可能记录 `command_enabled=false` 或 `wmp_action_sent=false`。它不属于本文
所说的“正式自动日志”。`logs/depth` 下的深度接收/录制日志又是另一套格式，也不按本文解析。

## 1. 文件约定

无参数运行正式入口时，每次启动都会新建一个文件：

```text
logs/real/go2wwmp_unitree_YYYYmmdd_HHMMSS_microseconds.jsonl
```

同时默认新建同名观测目录：

```text
logs/real/go2wwmp_unitree_YYYYmmdd_HHMMSS_microseconds_obs/
  manifest.json
  chunk_000000.npz
  chunk_000001.npz
  summary.json       # 正常退出后生成
```

例如：

```text
logs/real/go2wwmp_unitree_20260909_105804_619862.jsonl
```

文件名时间来自笔记本本地时间，表示程序生成默认文件名的时刻；它不是精确的 LowCmd
接管时刻，文件名中也没有时区。使用 `--log PATH` 可以指定文件，但同名文件会被覆盖，
因此正式实验建议继续使用自动命名。观测目录可以用 `--observation-dir PATH` 指定；
只有明确使用 `--no-observation-log` 才会关闭观测归档。为避免把两次实验混在一起，指定的
观测目录如果已经含有 `chunk_*.npz` 会直接报错；请为下一次实验换一个目录。

日志采用 **JSON Lines（JSONL）**：每一行都是一个完整 JSON 对象，行与行相互独立；整个
文件不是一个 JSON 数组，也没有表头和结尾摘要。正式入口在 WMP action 接管后约 50 Hz
写一行，并立即 `flush`。如果接管前取消或失败，文件可能存在但为空；运行中发生故障时，
文件通常在最后一个成功周期处直接结束，不会自动增加 `error` 行。

读取仍在写入的文件时，只处理已经以换行符结束的行。如果最后一行暂时解析失败，应等待
写入完成后重试，不要立即把它判定为永久损坏。

## 2. 一行代表什么

一行代表一次成功完成的 50 Hz WMP 控制周期，时序是：

```text
读取 LowState 和遥控器
  -> 子进程取得最新深度并执行 WMP
  -> 主进程收到 action/MotorCommand
  -> 更新 DdsDriver 的最新命令缓存
  -> 写入一行 JSONL
  -> 500 Hz LowCmd 线程异步重复发送最新缓存
```

因此 `wmp_action_sent=true` 的准确含义是：该候选命令已通过主进程并写入 DdsDriver 的
发送缓存。它不表示机器人返回了电机侧确认，也不表示实测关节一定达到目标。

当前正式日志每行有以下 27 个键。JSON 对象中的键顺序只方便人读，接口程序必须按键名
访问，不能依赖顺序。

## 3. 周期与状态字段

| 字段 | 类型/形状 | 单位 | 内容 |
|------|-----------|------|------|
| `event` | string | — | 当前固定为 `"step"` |
| `loop` | integer | 周期 | 接管后成功记录的周期号，从 1 开始连续递增 |
| `state_tick` | integer | 未定义 | 本周期所用 Unitree LowState 的原始 `tick`；在没有官方单位约定时只应作为不透明序号使用 |
| `state_age_ms` | number | ms | 主进程采样时，LowState 距离笔记本 DDS 回调接收时刻的本地年龄 |
| `command_enabled` | boolean | — | 命令输入是否处于使能状态；正式 Unitree 入口当前始终为 `true` |
| `wmp_action_sent` | boolean | — | 本周期候选 MotorCommand 是否已写入 DdsDriver 最新命令缓存；正式日志当前始终为 `true` |

航向保持另外记录 5 个字段：

| 字段 | 类型 | 单位 | 内容 |
|------|------|------|------|
| `heading_mode` | boolean | — | 本周期是否由航向模式生成最终 command |
| `heading_event` | string/null | — | 新开启为 `"enabled"`、新关闭为 `"disabled"`，其余周期为 null |
| `heading_target_yaw_rad` | number/null | rad | A 开启瞬间锁定的目标 yaw；关闭时为 null |
| `heading_current_yaw_rad` | number | rad | 本周期使用的 LowState IMU yaw |
| `heading_error_rad` | number/null | rad | 包角到 `[-pi,pi]` 的 `target-current`；关闭时为 null |

`loop` 只覆盖接管后的 action 周期。模型加载、首帧只读自检、等待 L2+R2、深度 session
同步和固定站姿缓存都不会写入该文件。期望频率约为 50 Hz，但日志没有逐行时间戳，不能仅用
`loop` 精确恢复每个周期的绝对时间或抖动。

## 4. 速度命令、网络输出和下发目标

| 字段 | 类型/形状 | 单位 | 内容 |
|------|-----------|------|------|
| `command` | number[3] | m/s, m/s, rad/s | 实际送入 WMP 的 `[vx, vy, vyaw]`，已经过最终裁剪 |
| `action` | number[16] | 无量纲 | 网络原始动作经 `[-100, 100]` clip 后的 16 维输出，使用 Ctrl 顺序 |
| `positions` | number[16] | rad | MotorCommand 位置目标，使用 DDS 顺序；轮关节位置项为 0 |
| `velocities` | number[16] | rad/s | MotorCommand 速度目标，使用 DDS 顺序；腿关节速度项为 0 |
| `kp` | number[16] | Unitree LowCmd Kp | 16 路命令 Kp，使用 DDS 顺序 |
| `kd` | number[16] | Unitree LowCmd Kd | 16 路命令 Kd，使用 DDS 顺序 |
| `inference_ms` | number | ms | 子进程中一次 `controller.step()` 的耗时 |
| `needs_depth_update` | boolean | — | 本周期 world model 是否实际消费了一张深度图 |

`command` 是遥控器映射后、真正进入策略的值，不是未经处理的摇杆值。当前范围为：

```text
vx    [-0.2, 1.0] m/s
vy    固定为 0 m/s
vyaw  [-1.0, 1.0] rad/s
```

航向模式开启时，`command` 不再来自 Ly/Rx，而固定 `vx=0.5`、`vy=0`，并按
`vyaw=clip(heading_error_rad,-1,1)` 计算。按 B 关闭后恢复原装遥控器映射。详见
[guide 23](23_go2wwmp_heading_mode.md)。

`inference_ms` 包含 actor 推理；当 `needs_depth_update=true` 时也包含深度处理和 world-model
更新。它不包含进程间通信、主循环等待、DDS 缓存更新、500 Hz 发送、日志写入或图像显示。
当前设计约每 5 个 policy 周期更新一次深度，但首帧只读自检也会推进控制器状态，因此对接程序
应直接读取 `needs_depth_update`，不要假设它必然等于某个固定的 `loop % 5`。

### 4.1 `action` 的 Ctrl 顺序

| 索引 | 关节 | 索引 | 关节 |
|-----:|------|-----:|------|
| 0 | FL hip | 8 | RL hip |
| 1 | FL thigh | 9 | RL thigh |
| 2 | FL calf | 10 | RL calf |
| 3 | FL wheel | 11 | RL wheel |
| 4 | FR hip | 12 | RR hip |
| 5 | FR thigh | 13 | RR thigh |
| 6 | FR calf | 14 | RR calf |
| 7 | FR wheel | 15 | RR wheel |

`action` 到电机目标的换算为：

```text
腿关节 position = INITIAL_JOINTS_POS + action * 0.25 rad
腿关节 velocity = 0, Kp = 50, Kd = 1

轮关节 position = 0
轮关节 velocity = action * 10 rad/s, Kp = 0, Kd = 0.5
```

### 4.2 MotorCommand 的 DDS 顺序

`positions`、`velocities`、`kp`、`kd` 已经从 Ctrl 顺序映射为机器人 DDS 顺序：

| 索引 | 关节 | 索引 | 关节 |
|-----:|------|-----:|------|
| 0 | FR hip | 8 | RR calf |
| 1 | FR thigh | 9 | RL hip |
| 2 | FR calf | 10 | RL thigh |
| 3 | FL hip | 11 | RL calf |
| 4 | FL thigh | 12 | FR wheel |
| 5 | FL calf | 13 | FL wheel |
| 6 | RR hip | 14 | RR wheel |
| 7 | RR thigh | 15 | RL wheel |

这是最容易对接错误的地方：`action[i]` 与 `positions[i]`/`velocities[i]` 并不表示同一个
关节。若要逐关节比较，应先按 `config/go2w_config.py` 中的 `DDS_IDX_FROM_CTRL` 映射。

## 5. 深度字段

| 字段 | 类型 | 单位 | 内容 |
|------|------|------|------|
| `depth_session` | integer | — | Orin 深度发布进程本次启动的 session ID |
| `previous_depth_session` | integer | — | worker 在处理当前帧前保存的 session ID |
| `session_changed` | boolean | — | 当前 `depth_session` 是否不同于上一 session |
| `depth_frame` | integer | 帧 | Orin 发布的源帧编号 |
| `depth_valid_ratio` | number | 0–1 | 64×64 图中 valid 像素比例，仅作质量诊断 |
| `depth_invalid_pixels` | integer | 像素 | 64×64 图中 `valid=0` 的像素数 |
| `depth_local_age_ms` | number | ms | worker 采样时，深度帧距离笔记本 DDS 回调接收时刻的本地年龄 |
| `depth_source_processing_ms` | number | ms | Orin 上从采集时间到发布时间的单机处理耗时 |

深度图固定为 64×64，所以通常满足：

```text
depth_invalid_pixels = 4096 * (1 - depth_valid_ratio)
```

浮点显示可能有很小的舍入差异。`depth_valid_ratio` **不会触发停机或阻尼**；无效像素仍按
当前 pipeline 的约定以 2 m 远端值进入网络，同时保留 valid mask 的诊断统计。日志不保存
主 JSONL 不保存 64×64 深度矩阵和 mask；观测归档会按第 7 节保存深度更新帧，因此只靠主 JSONL
不能重建当时画面。

`depth_local_age_ms` 使用笔记本单机单调时钟，不受 Orin 与笔记本时钟未同步的影响；当前运行
要求深度年龄不超过 100 ms。`depth_source_processing_ms` 的捕获和发布时刻都来自 Orin，
同样不需要跨机器对时。两者不能直接相加成严格的端到端相机延时。

同一 session 内 `depth_frame` 应总体递增，但 50 Hz 控制与深度发布频率不同，读取“最新帧”
可能出现跳号或重复，消费者不应强制要求每行恰好 `+1`。

正式入口在 action 阶段发现 session 改变时，会在发送和记录该周期之前结束并进入阻尼。因此
一份正常的正式日志中，`session_changed` 应始终为 `false`，两个 session 字段相等；session
改变本身只会表现为文件停止增长和终端报错，而不会作为一行 `session_changed=true` 被保存。

## 6. 当前明确没有保存的数据

以下数据目前不在自动 JSONL 中：

- 主 JSONL 中没有 LowState 的 16 路实测 `q/dq`、IMU 四元数和角速度；这些数据会写入旁边的
  观测 chunk；`tau`、IMU 加速度/RPY、电池数据仍未写入观测归档；
- 电机实际反馈或 MotorCommand 的硬件确认；
- 主 JSONL 没有 64×64 深度图和 valid mask；观测归档只在 `needs_depth_update=true` 的行保存
  当时接收的原始米制深度和 valid mask；world model 的一帧延迟选择仍按 pipeline 重算；屏幕预览图不保存；
- 原装遥控器原始摇杆、按钮字节和电池状态；
- 主 JSONL 没有每行墙钟时间和单调时间；观测归档保存两种 timestamp，但不保存每个 500 Hz
  LowCmd 写出的时间戳；
- 主 JSONL 没有 checkpoint metadata；观测目录的 `manifest.json` 保存模型路径、SHA-256、
  schema 和数组形状，但仍不保存网卡、DDS domain/topic；
- 最终退出原因、异常堆栈、急停或阻尼开始时刻。

模型 SHA-256 只在启动终端的 `[READY]` 行打印，不写入 JSONL。因此需要严格复现实验时，至少
应同时记录日志文件名、模型文件/哈希、现场视频和终端输出。当前 JSONL 不能单独用于：证明
实测电机跟随目标、精确同步外部相机/力传感器、回放原始深度，或完整还原最后一次故障。

还要注意一个边界：程序先更新命令缓存，再写日志。如果缓存更新失败，本周期不会有日志；如果
缓存更新成功后恰好发生磁盘写入故障，最新一条命令可能已经进入 500 Hz 路径但最后一行缺失。

## 7. 观测归档（`*_obs/`）

正式入口默认保存观测归档。每个 `chunk_XXXXXX.npz` 是约 250 个控制周期（约 5 秒）的
未压缩 NumPy 容器，写入采用临时文件加原子改名；观测记录器在 worker 进程内用后台线程写盘，
不会在每个 policy 周期同步压缩深度图。

每个 chunk 包含：

| 数组 | 形状/类型 | 内容 |
|------|-----------|------|
| `timestamp_wall_ns` | `[N] int64` | Unix 墙钟时间戳 |
| `timestamp_monotonic_ns` | `[N] int64` | 笔记本单调时钟时间戳，可用于时延/周期分析 |
| `loop`、`state_tick` | `[N] int64` | 与主 JSONL 对齐的周期号和 LowState tick |
| `state_age_ms` | `[N] float32` | 采样时 LowState 年龄 |
| `command` | `[N,3] float32` | 实际进入 WMP 的 `[vx,vy,vyaw]`，属于策略输入 |
| `joint_positions_dds` | `[N,16] float32` | DDS 顺序实测关节位置 |
| `joint_velocities_dds` | `[N,16] float32` | DDS 顺序实测关节速度 |
| `imu_quat_wxyz` | `[N,4] float32` | 实测 IMU 四元数 |
| `imu_gyro_xyz` | `[N,3] float32` | 实测 IMU 角速度 |
| `prop` | `[N,37] float32` | WMP 本体/命令观测，已按训练语义缩放和 clip |
| `obs_now` | `[N,53] float32` | actor 当前观测（`prop + last_action`） |
| `obs_history` | `[N,250] float32` | actor 历史输入，5×50 |
| `wm_feature` | `[N,512] float32` | actor 使用的 world-model context |
| 深度诊断数组 | `[N]` | session、frame、valid、invalid、age、source processing |
| `needs_depth_update` | `[N] bool` | 当前周期是否消费新深度 |
| `depth_update_rows` | `[M] int64` | 本 chunk 中真正保存深度的行号 |
| `depth_image_m` | `[M,64,64] float32` | 对应更新周期接收的原始米制深度；只保存 `needs_depth_update=true` 的行 |
| `depth_valid` | `[M,64,64] uint8` | 与深度图对应的 valid mask |

这里的 `M` 通常约为 `N/5`。深度不在非更新周期重复存储，但每个周期仍保存深度 session、
frame 和质量/年龄信息，所以可以将深度帧与策略观测按 `loop` 对齐。保存的是原始米制深度；
WMP 的 clip、中心化和一帧延迟仍可由离线脚本按照当前 pipeline 重算。
这份归档是“策略观测记录”，不是相机发布端的 60 Hz 全量录制；若需要分析每一张 DDS 深度帧，
继续使用 `scripts/depth/record_scene.py` 生成的深度录制文件。

观测归档明确**不保存** `action`、`positions`、`velocities`、`kp`、`kd` 和 `torques`；
这些是发送侧数据，后续可根据 checkpoint、`obs_now`、`obs_history` 和 `wm_feature` 重新计算。
主 JSONL 仍保留这些诊断字段，以便现场快速检查；如果只希望保存观测文件，可继续保留主 JSONL
作为控制故障证据，也可在实验后单独清理它。

读取一个 chunk：

```python
import numpy as np
from pathlib import Path

paths = sorted(Path("logs/real").glob("go2wwmp_unitree_*_obs/chunk_*.npz"))
if not paths:
    raise FileNotFoundError("没有找到观测 chunk；先运行一次正式入口")
chunk = np.load(paths[0])
print(chunk["obs_now"].shape)          # (N, 53)
print(chunk["obs_history"].shape)      # (N, 250)
print(chunk["depth_image_m"].shape)    # (M, 64, 64)
print(chunk["depth_update_rows"])      # 深度对应的 chunk 内行号
```

把多个 chunk 拼成画图用的连续序列：

```python
from pathlib import Path
import numpy as np

paths = sorted(Path("logs/real").glob("go2wwmp_unitree_*_obs/chunk_*.npz"))
if not paths:
    raise FileNotFoundError("没有找到观测 chunk")
timestamp_parts = []
obs_parts = []
valid_parts = []
for path in paths:
    with np.load(path) as chunk:
        timestamp_parts.append(chunk["timestamp_wall_ns"].copy())
        obs_parts.append(chunk["obs_now"].copy())
        valid_parts.append(chunk["depth_valid_ratio"].copy())
timestamps = np.concatenate(timestamp_parts)
obs_now = np.concatenate(obs_parts)
valid_ratio = np.concatenate(valid_parts)
print(timestamps.shape, obs_now.shape, valid_ratio.shape)
```

深度数组是稀疏保存的；拼接深度时要给每个 chunk 的 `depth_update_rows` 加上此前 chunk 的
帧数，不能把 `depth_update_rows` 直接当作全局行号。

遍历整个观测目录时，应按 `chunk_*.npz` 的数字顺序读取，并用每个 chunk 的 `loop` 或 timestamp
连接，而不是假设目录文件系统顺序。`manifest.json` 是机器可读的格式说明；`summary.json`
只在正常关闭后写出，异常中断时仍可直接使用已经完成的 chunk。

## 8. Python 读取主 JSONL 示例

### 8.1 找到最新的自动日志并查看最后一行

下面代码只匹配正式入口的时间戳命名，避免误选手工命名的 print-only/短测日志：

```python
import json
from pathlib import Path

paths = list(Path("logs/real").glob("go2wwmp_unitree_20*.jsonl"))
if not paths:
    raise FileNotFoundError("没有找到 Go2WWMP 自动日志")

path = max(paths, key=lambda item: item.stat().st_mtime)
last = None
with path.open("r", encoding="utf-8") as stream:
    for line in stream:
        if not line.endswith("\n"):
            break  # 正在写入时，等待末行完成
        if line.strip():
            last = json.loads(line)

if last is None:
    raise ValueError(f"日志为空或尚无完整记录: {path}")

print("file:", path)
print("last loop:", last["loop"])
print("command:", last["command"])
print("depth frame/valid:", last["depth_frame"], last["depth_valid_ratio"])
```

### 8.2 流式检查完整性并汇总

长时间日志不建议一次性全部读入内存。以下示例逐行处理，并检查正式格式的关键约束：

```python
import json
from pathlib import Path

path = Path("logs/real/go2wwmp_unitree_20260909_105804_619862.jsonl")
# 换成需要分析的实际日志路径。
required = {
    "event", "loop", "state_tick", "state_age_ms",
    "command", "action", "positions", "velocities", "kp", "kd",
    "inference_ms", "needs_depth_update",
    "depth_session", "previous_depth_session", "session_changed",
    "depth_frame", "depth_valid_ratio", "depth_invalid_pixels",
    "depth_local_age_ms", "depth_source_processing_ms",
    "command_enabled", "wmp_action_sent",
    "heading_mode", "heading_event", "heading_target_yaw_rad",
    "heading_current_yaw_rad", "heading_error_rad",
}

count = 0
depth_updates = 0
min_valid = 1.0
max_inference_ms = 0.0

with path.open("r", encoding="utf-8") as stream:
    for line_number, line in enumerate(stream, start=1):
        if not line.endswith("\n"):
            break  # 允许读取仍在增长的文件
        if not line.strip():
            continue
        row = json.loads(line)
        missing = required - row.keys()
        if missing:
            raise ValueError(f"line {line_number}: missing {sorted(missing)}")
        if row["event"] != "step" or row["loop"] != count + 1:
            raise ValueError(f"line {line_number}: event/loop 不连续")
        if any(len(row[key]) != size for key, size in {
            "command": 3, "action": 16, "positions": 16,
            "velocities": 16, "kp": 16, "kd": 16,
        }.items()):
            raise ValueError(f"line {line_number}: 数组长度错误")

        count += 1
        depth_updates += int(row["needs_depth_update"])
        min_valid = min(min_valid, row["depth_valid_ratio"])
        max_inference_ms = max(max_inference_ms, row["inference_ms"])

if count == 0:
    raise ValueError(f"日志为空或尚无完整记录: {path}")

print("rows:", count)
print("depth updates:", depth_updates)
print("min valid ratio:", min_valid)
print("max inference ms:", max_inference_ms)
```

## 9. 对接规则

建议后续读取器遵守以下约定：

1. 以换行符作为记录完成标志，一行一条消息；允许文件在任意完整行结束。
2. 按字段名读取，不依赖 JSON 键顺序；遇到未知新字段应忽略，以便向前兼容。
3. 正式格式缺少上述必需字段或数组长度不符时，应标记为不兼容/不完整，而不是静默补零。
4. `depth_session`、`previous_depth_session` 等整数可能超过 JavaScript 安全整数
   `2^53-1`。Python `json` 可以精确保留；JavaScript 端不要用普通 `Number` 作为 session
   身份键，应使用支持大整数的 JSON 解析器，或在 ETL 时把原始整数字面量转成字符串/BigInt。
5. `action` 使用 Ctrl 顺序，MotorCommand 数组使用 DDS 顺序；数据库字段名中建议显式保留
   `_ctrl` 和 `_dds` 后缀。
6. `positions`/`velocities` 是目标，不是反馈；分析跟踪误差必须另行采集 LowState 实测值。
7. 不要把低 `depth_valid_ratio` 当作无效周期。它是场景质量信息，当前控制策略仍会使用该帧。

## 10. 容量和归档

已验收样本 `go2wwmp_unitree_20260909_105804_619862.jsonl` 有 1894 行、约 2.81 MB，平均
约 1.48 KB/周期。按 50 Hz 粗略估算：

```text
约 4.45 MB / 分钟
约 267 MB / 小时
```

观测归档的实测基准约为 `7.8 KB/周期`，即约 `23–25 MB/分钟`；它已经把深度限制为每 5 个
周期保存一次。主 JSONL 与观测归档合计约 `28–30 MB/分钟`，主要成本是磁盘空间，不是 CPU：
观测 chunk 的整理约 8 ms/5 秒，完整写盘约 18 ms/5 秒且由后台线程执行。若 SSD 空间有限，
可用 `--no-observation-log` 关闭归档，但这会失去后续完整观测复盘能力。

实际大小会随浮点数字符串长度略有变化。该样本 gzip 后约为原文件的 24.5%，因此长期实验后
可以压缩已经结束的日志；不要压缩程序仍在写入的文件。应定期检查 `logs/real` 可用空间，
避免磁盘写满导致已经更新命令缓存但日志缺行。

## 11. 当前格式版本约定

本文把上述 22 字段称为“当前正式格式”。日志内暂时没有 `schema_version` 或文件级 metadata，
所以读取器应通过必需字段和数组长度识别格式。以后如果修改日志结构，应优先新增字段而不是
改变现有字段含义；若必须改变语义，应同时增加显式 `schema_version`，并更新本文和读取示例。
